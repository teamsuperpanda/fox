# ADR 0001: Shared storage and backup package with Pandoo

- **Status:** Proposed (evaluation complete, awaiting maintainer sign-off)
- **Date:** 2026-11-07
- **Issue:** [teamsuperpanda/fox#150](https://github.com/teamsuperpanda/fox/issues/150), cross-repo [teamsuperpanda/pandoo#108](https://github.com/teamsuperpanda/pandoo/issues/108)
- **Deciders:** Team Super Panda

## Context

Fox and Pandoo are both offline-first Flutter apps that use Hive as their only
data store. Both are heading into the same storage work at the same time:

| Concern | Fox | Pandoo |
|---|---|---|
| Boxes | `notes_db`, `folders_db`, `settings_db`, plus `schema_db` in #79 | `lists`, `settings_db` |
| Models | `Note`, `Folder`, `Settings` | `ListModel`, `TodoItem`, `Settings` |
| Adapters | Handwritten, field-count aware, tolerant readers in #79 | Generated by `hive_generator`, hard-casts, defaults applied by the generated `read` |
| Schema version | No version key today; #79 adds one plus ordered migrations | No version key; #49 asks for the same |
| Error handling | Services rethrow, callers catch partially | Services rethrow or `debugPrint`; #56 asks for one result type |
| Startup failure | #80: corrupt record bricks startup | #36: splash never removed on a failed box open |
| Export / backup | Nothing; #75 adds a versioned JSON archive plus Markdown | Nothing; #42 adds a versioned JSON backup, #44 adds import |
| Import / merge | #76 | #44 |

The duplicated work is not the models or the UI. It is the rules around the
data, which are exactly the rules that must not drift between two apps owned by
the same team:

1. A schema version key, written once and checked before the first read.
2. Ordered, idempotent migrations with a hard failure when a step is missing or
   the file was written by a newer app.
3. Tolerant field readers so an old box still opens after a model change.
4. A single result type instead of a mix of rethrows and swallowed errors.
5. A versioned backup envelope with validation, and merge or replace semantics.

Fox #79 already sketches 1, 2, 3 and part of 5 in about 170 lines
(`lib/services/schema_migrations.dart`, `lib/models/adapter_utils.dart`,
`lib/services/data_export.dart`). Pandoo needs the same logic in #49, #56, #42
and #44. Writing it twice guarantees two subtly different migration rules, and
the first time they disagree a user loses a list or a note.

The rest of both apps overlaps much less: the models differ in shape, Pandoo
uses generated adapters, and the editor, ordering, undo and theme semantics are
different products.

## Decision

Adopt **option A: a narrow, pure-Dart package**, named `panda_store`, containing
only the storage rules and the backup envelope. Do not extract models,
adapters, serialisers, widgets, themes or undo behaviour.

The package owns:

- **Schema version and migration runner.** A version key contract, a
  `runMigrations(from:, to:, steps:)` function, a missing-step exception and a
  newer-schema exception. The apps supply the steps and the box handles.
- **Tolerant field readers.** `readString`, `readBool`, `readInt`, `readDate`
  and `readStringList`, used by handwritten adapters.
- **A storage result type.** A sealed success or failure value with a code and
  a message, so services stop choosing between rethrowing and `debugPrint`.
- **A versioned backup envelope.** `{"format": "panda-backup", "version": 1,
  "app": "...", "exportedAt": "...", "data": ...}`, schema validation with
  actionable errors, and merge-by-id helpers. Each app keeps its own
  map-to-model serialisers.

The package must be MIT licensed. Fox is MIT after #65; Pandoo is PolyForm
today, and a PolyForm package could not be consumed by an MIT Fox. MIT is
compatible with both.

### Sequencing

1. Land Fox #79 and Pandoo #49 independently. They are the reference
   implementations and the source of the first shared tests.
2. Create `packages/panda_store` in the Fox repository with the migration
   runner, tolerant readers, result type and envelope, plus the v1 fixtures
   already written for #79.
3. Consume it from Fox through a path dependency. No behaviour change: the
   existing `schema_migrations.dart` and `adapter_utils.dart` become thin
   re-exports or are deleted.
4. Consume it from Pandoo through a git dependency on the Fox repository until a
   third app appears. Publishing to a private package registry is deferred: one
   consumer is a path dependency, two consumers are a git dependency, three
   consumers justify a registry.

Do this before either app adds more nullable fields, as the issue asks.

## Options considered

### A. Shared pure-Dart package (chosen)

- **Cost:** roughly 500 lines of package code with tests, plus adoption work.
  Estimate 2 to 3 days for the package and tests, half a day for Fox, one to one
  and a half days for Pandoo because its adapters are generated and its boxes
  are laid out differently.
- **Benefit:** one migration rule, one envelope, one result type, one fixture
  suite. A bug fixed once is fixed in both apps.
- **Risk:** two-repo release coordination. Mitigated by pinning the git ref and
  bumping it deliberately, and by keeping the package small enough to read in
  one sitting.

### B. Copy the code into both repositories

- **Cost:** lowest to start, about half a day per repo.
- **Benefit:** no cross-repo dependency, no package release process.
- **Risk:** the copy drifts. The first divergence would be in the migration
  ordering or the envelope version, which is the worst place to diverge. The
  issue exists precisely to avoid this.

### C. Keep separate, share only tests and documentation

- **Cost:** lowest, documentation only.
- **Benefit:** each app stays free to solve storage its own way.
- **Risk:** no enforcement. The shared rules live in prose that nobody runs,
  and Pandoo's generated adapters will diverge from Fox's handwritten ones
  silently.

## Consequences

- One more package to version and test. It is pure Dart with a single `hive`
  dependency, so it runs in plain `dart test` and does not pull in Flutter.
- Both apps gain the same failure messages and the same backup format, so a
  backup from one app can be recognised (and rejected with a clear error) by the
  other.
- The package cannot know about `Note`, `Folder`, `ListModel` or `TodoItem`.
  Anything model-specific stays behind a callback or an interface the app
  implements.
- Pandoo's generated adapters stay generated. The tolerant readers only help
  handwritten adapters; the migration runner and envelope help both apps
  regardless of adapter style.
- Fox #79 and Pandoo #49 must land first. If either is rejected, the package
  loses its reference implementation and should be reconsidered.

## What would have to change

### In Fox

- Add `packages/panda_store` with `pubspec.yaml`, MIT licence header, tests and
  the v1 Hive fixtures from #79.
- Replace the bodies of `lib/services/schema_migrations.dart` and
  `lib/models/adapter_utils.dart` with calls into the package, or delete them.
- Make `StorageService` use the package's migration runner and result type.
- Make the #75/#76 export and import use the package envelope, keeping the
  note and folder serialisers in `lib/services/`.
- Add the package to `analysis_options.yaml` overrides if the lint sets differ.

### In Pandoo

- Add the git dependency on the Fox repository, pinned to a tag or commit.
- Replace the migration skeleton from #49 with the package runner.
- Adopt the package result type in `StorageService` and `SettingsService` (#56).
- Use the package envelope for the #42 export and #44 import, keeping list and
  item serialisers in Pandoo.
- Add the same v1 fixture test Fox uses, with Pandoo's models, so both apps
  prove they open the same fixture and run the same migration.

### Explicitly out of scope

- Note and list models, adapters, serialisers.
- Widgets, themes, spacing tokens, golden frames.
- Undo semantics, list ordering and note colours.
- Any change to the on-disk format beyond the schema key and envelope.
